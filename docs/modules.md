# Module map

Per-file dependency table. "Uses" lists project modules from static
top-level imports only (stdlib and third-party omitted). `(lazy)` marks a
function-level import that does not fire at module load. Entry-point and
dynamic-import edges (`_import_app`, argparse dispatch) are noted by hand.
An `if TYPE_CHECKING:` import is not a runtime edge and is recorded by hand
or left out.

The table is machine-read: `tools/invariants.py`'s `modules.doc` rule reports
an app module with no row, a row with no module, a project import missing from
the "Uses" cell, and a row whose cell count is wrong (see
[invariants.md](invariants.md)). Write every module name inside backticks —
`utils.config` or a `utils.{config,theme}` brace group — because those are
the only tokens the checker reads; prose around them is not parsed.

To regenerate the raw edge list while updating this file:

```bash
grep -rn "^from \|^import " app/ --include="*.py"
```

## Cross-layer exceptions

Almost every edge follows the downward direction in README.md. The
deviations, each deliberate:

1. `services.auth_setup.save_spotify_credentials` delegates through a
   lazy import to `integrations.spotify.spotify.save_spotify_credentials_file`.
   Keeps exactly one credential writer, inside the plugin repo.
2. `ui.login_ui._browser_file_ready` reads
   `integrations.youtube_music.youtube_music.browser_file_candidates()`
   lazily and falls back to the `auth_setup.BROWSER_FILE`/`YT_MUSIC_FILE`
   constants if the plugin repo is missing.
3. `KeybindCallbacks` lives in `controllers/keybind_registry.py` next to
   the registry that stores one per playlist. It used to sit in its own
   `controllers/callbacks.py` so `keybind_registry` could stay "pure
   data", but the UI already imports `keybind_controller`, so the split
   bought a `TYPE_CHECKING` import and a 46-line module rather than a
   layer boundary. Both ends of the contract need the type, so the row
   that defines it also lists it.
4. `utils/config.py` statically imports `services/profile_store.py` on
   startup and calls `initialize()`. This is an upward edge (utils -->
   services) that the other modules need: `profile_store` is the single
   place the active profile is resolved at import, and every path-holding
   module (services + utils.config) must derive from it. It is safe only
   because `profile_store` has no app imports (stdlib + platformdirs), so
   it cannot create a cycle. All other `services.*` imports of
   `profile_store` are already in the services layer.
5. `utils/i18n.py` imports `services/profile_store` statically for the same
   reason and with the same guarantee: `I18N_DIR = cfg_dir() / "i18n"` is a
   module-level constant, so the edge cannot be made lazy without turning
   every catalog lookup into a directory resolution.
6. `utils/thumbnail.py` reaches `services/duplicate_check.py` and
   `services/song_manager.py` through **lazy** imports (both marked `(lazy)`
   in its row above), so the add path and the thumbnail cache agree on what a
   song identity is and cannot drift; a module-level import would be circular,
   since `song_manager` uses the thumbnail service to fill its cache.

Items 4-6 are the only upward edges inside `app/`, and
`tools/invariants.py`'s `layer.import` rule enforces that: any *new* upward
edge is a finding unless the importing file is exempted with a reason (see
docs/invariants.md).
