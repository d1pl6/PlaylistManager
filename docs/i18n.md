# i18n: how translations work (and how to add one)

Every user-facing string in `app/` goes through `utils/i18n.py` — there is no
gettext, no `_()` anywhere. This page is the translation contract (operational
rules included); the module map lives in [modules.md](modules.md).

## The catalog files (three layers, user wins)

1. User catalog — `<profile cfg_dir>/i18n/<lang>.ini` (profile-aware,
   created on first use)
2. Bundled catalog — `app/i18n/<lang>.ini` (ships with the repo, read-only)
3. Code-side English defaults — `DEFAULT_STRINGS` in `app/utils/i18n.py`

A lookup (`tr(key)`, `trn(key, n)`, `tr_status(code)`) walks 1 → 2 → 3 and
returns the first hit; an entirely unknown key renders as the key itself
(never raises). **Missing keys self-heal**: reading a catalog through
`set_language()` writes English placeholders for every missing key into the
user catalog, so a translator's workspace is always complete — English placeholders and
all, nothing missing.

You never maintain the user and bundled catalogs in sync — they are a stack,
not two copies. The user file is created **once** (first launch with that
language; `ensure_i18n_file` only writes when something changed, so later
launches are read-only), then self-heals as the key set grows. **Stale
placeholders yield to the bundle**: when the bundled file gains a
translation for a key the user file only holds as a heal-artifact English
placeholder (value byte-identical to the English default), the next heal
prunes that row so the bundle's German shows through; genuine user edits
(value ≠ default) are deliberate overrides and always survive. Comments
(lines starting with `;`/`#`) persist in the bundled files forever (never
rewritten) but are dropped from user catalogs by a heal rewrite — put
annotations in the bundled file or the example template.

All catalogs are `ConfigParser` INI, one `[strings]` section. Values with a
literal `%` are stored `%%`-escaped (BasicInterpolation unwraps on read) —
never write a bare `%` into a catalog. Surrounding whitespace and per-line
indentation inside multi-line values are stripped by the format; the English
defaults with padding (`' · {pct}% match'`) render unpadded in every
translated catalog (cosmetic, accepted).

## Language selection

`settings.ini` `[language] lang = <code>` picks the language at startup
(`set_language` runs in both `App.__init__` and `app/main.py:main()`).
"en" needs no file — it IS the code defaults. The Settings → Appearance
language combobox writes `lang` live; the change applies after a restart
(same rule as ui_scale/font). Complications are looked up by native name via
`language_display(code)` / `language_code_for(display)`.

## The translation workflow

```bash
python tools/i18n_report.py export              # (re)build the template
python tools/i18n_report.py diff de             # what is still English?
python tools/i18n_report.py diff de --list      # ... full key list
python tools/i18n_report.py diff de --write-missing=missing_de.ini # write missing in file
python tools/i18n_report.py diff de --strict    # exit 1 while gaps remain
```

1. **`export`** regenerates `app/i18n/example.ini` — the English template
   holding every translatable key — from `DEFAULT_STRINGS`. It only rewrites
   when content changed, so an untouched tree leaves no git diff. A pytest
   pins the committed template to the code defaults; if it fails, run
   `export` again. `example` is never offered as a language.
2. **`diff <lang>`** reports `total / translated / still English` against
   the language's *resolved* catalog (bundled overlaid by the user catalog —
   what the speaker actually sees), splitting gaps into:
   - `missing` — no row for the key anywhere (normally 0 after self-heal)
   - `placeholder` — row exists but still shows the English default
   - `identity` — deliberately identical (proper nouns/loanwords, e.g.
     `app.title` = "PlaylistManager"); counted as translated
3. Fill translations in `app/i18n/<lang>.ini` (ships to everyone) or
   `<profile cfg_dir>/i18n/<lang>.ini` (personal overrides — wins over
   bundled). Restart the app to see them.

## Plural rules

Count-bearing strings use `trn(key, n)` with the catalog rows
`<key>.one` / `<key>.other`; `{count}` is auto-injected. German also needs
the two forms for 1 vs not-1 (sentence templates may use `{count}` inside,
e.g. the manage-footer rows).

## Keeping the English source of truth honest

- `tests/test_i18n.py::TestCatalogConsistency` statically scans `app/`:
  every `tr("key")` / `trn("key")` literal must exist in `DEFAULT_STRINGS`,
  and every default key must have a call site (keep it that way).
- `tests/test_i18n_tool.py` pins `example.ini` to `DEFAULT_STRINGS` and
  unit-tests the diff buckets, the exporter, and the CLI.

## Catalog contract (operational rules)

- **Add a catalog row in the same commit as any new `tr()` call.** All keys
  live in `DEFAULT_STRINGS` (`utils/i18n.py`) as the English source of truth —
  `tests/test_i18n.py::TestCatalogConsistency` statically scans `app/` and
  fails on any `tr("key")`/`trn("key")` literal missing from the dict, and the
  reverse holds too (every key has a call site; keep it that way).
- **Engine rules**: values are read at widget-creation time only (same as the
  `C[...]` colors in [theming.md](theming.md)); `tr()` formats only when kwargs
  are passed (literal `{braces}` are safe); `%` in values is escaped to `%%`
  when writing INI catalogs — never write a bare `%` that reaches
  `parser.set()`.
- **Do not translate strings used as stored values/keys/identifiers** (sort
  keys, mode keys, playlist names). Display-only labels like combobox rows use
  per-key catalog rows (`settings.sort_key_*`, `settings.thumbnail_mode_*`,
  `settings.removal_mode_*`) and resolve the label→key reverse-map from the
  same translated mapping.
- **Count-bearing CLI/UI strings use `trn()`** — never hand-rolled `"...(s)"`
  or `{'s' if n != 1}`; the manage-integrations footer and the uninstall
  report join `trn()` item rows into one translated sentence template per
  case.
- **`user_log` calls are lazy**: pre-format via `tr()`/`trn()` and pass the
  result as the only positional (no `%`-style args).
- **`tr_status(code)`** renders the stable card-status codes
  (`CARD_STATUS_KEYS`); opaque plugin/flow messages pass through unchanged.
- The bundled example catalog `app/i18n/de.ini` (read-only, ships in the repo)
  shows every shape — English defaults, templates, `{count}` plurals, umlauts.

## Out of scope by design

- Integration plugin flow/result messages stay English; they surface
  verbatim through `tr_status()`'s pass-through at the flow→UI boundary.
  Translating them is a separate (future) flow→UI-code rework.
- Live language switching is restart-only.
